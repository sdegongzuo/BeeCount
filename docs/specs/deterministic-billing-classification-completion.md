# Issue #7：确定性分类与待分类补正闭环

## 目标

图片分享记账不调用运行时 AI 或本地模型，也能稳定生成分类与可搜索的结构化摘要。分类证据不足时仍立即创建交易，以“其他”作为当前分类，并留下可发现、可同步、可补正的结构化待分类状态。

## 决策

### 1. 待分类是交易状态，不是备注文本

`transactions` 增加非空布尔字段 `needs_classification`，默认 `false`。图片记账命中 fallback“其他”时写 `true`，任何可靠分类写 `false`。

该字段进入交易同步 payload。旧数据库升级时，将历史 `details_text` 含 `待分类：是` 的交易回填为 `true`，并停止为新交易写入这一魔法字符串。历史文本不在迁移中改写，避免破坏用户数据。

### 2. 只有金额和时间是建账前关键字段

`TransactionStageProcessor` 只在金额缺失/非正数或时间缺失时进入 `awaiting_confirmation`。`no_rule_match`、`low_confidence`、`missing_payment_channel` 与分类不确定均不得阻塞交易创建。

`fastBillingAccepted` 仍保留为规则质量与诊断信号，但不再承担“能否创建交易”的总门禁。

### 3. 待分类必须可发现

Repository 提供当前账本的待分类查询/监听。图片分享在主 Flutter engine 中创建交易后，如果交易仍待分类，立即发出待分类 transaction ID；应用启动或恢复时也查询遗留记录并打开最早一条，避免 headless 创建后丢失入口。

UI 展示交易的图片证据（存在时）、结构化摘要、金额、时间和分类选择。用户可以：

- 只修正当前交易；
- 修正并记住为当前账本规则；
- 修正并记住为全局规则。

完成后原子更新交易分类、清除 `needs_classification`，并登记 transaction update change。记忆规则仅在用户明确选择时写入，目标分类使用稳定 `category.syncId`。

### 4. 规则匹配键与来源

个人分类规则的匹配文本按以下顺序取第一个非空值：`merchant_full_name`、`counterparty`、结构化摘要中的商户字段。不能用用户自由补充文本作为分类规则条件，避免个人备注意外改变分类行为。

分类优先级保持：当前账本个人规则 → 全局个人规则 → 页面规则 → 商户词典 → 全文关键词 → 其他。相同作用域内优先更长的匹配文本。

### 5. 结构化摘要与个人补充信息分离

图片交易的主备注只由图片中可验证的商户、商品、门店、出发站和到达站生成。用户补充信息合并进 `details_text` 的独立 `补充信息` 行；个人备注偏好保存在独立 store，并只在用户明确选择“记住备注”时更新。

分类记忆、提取规则记忆和备注偏好是三个独立选择，不能再由一个总开关同时控制。
